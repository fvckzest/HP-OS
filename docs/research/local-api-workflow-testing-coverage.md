The repository is still planning documentation; it contains no HP-OS application or test suite ([README](https://github.com/fvckzest/HP-OS/blob/8a96e39666a80e82c1d7e16b99976e5e00c522c1/README.md)). ## Evidence boundaries

Local API verification should exercise the same HTTP boundary used by the application against real local test PostgreSQL, with a controlled clock and simulated Site reports. It should assert response status and body, then query subsequent public/admin state. It should exercise the scheduler's bounded HP-OS processing entry point, including after process restart. It should never inspect private functions or SQL structure as the proof. These are the approved testing boundaries in [issue #22](https://github.com/fvckzest/HP-OS/issues/22), supported by the contract verification matrix and technology sequence ([contract verification](https://github.com/fvckzest/HP-OS/blob/8a96e39666a80e82c1d7e16b99976e5e00c522c1/docs/api/api.md#contract-verification-and-boundaries), [technology](https://github.com/fvckzest/HP-OS/blob/8a96e39666a80e82c1d7e16b99976e5e00c522c1/docs/technology.md)).

“LMNL call” means an incoming server-to-server request from the LMNL backend. Public browser and staff journeys call LMNL; the browser never receives the HP-OS key and there is no browser-facing HP-OS API in the first contract ([backend access](https://github.com/fvckzest/HP-OS/blob/8a96e39666a80e82c1d7e16b99976e5e00c522c1/docs/api/api.md#backend-access)). In a local API test, LMNL behavior can be represented by an authenticated HTTP client and simulated provider, email, or Wallet reports. That proves HP-OS behavior only.

The following require LMNL or an actual integration in addition to the local API:

- LMNL staff authorization, buyer and door routes, presentation, token handling, email templates, current page state, and provider callback/outbox execution require the LMNL backend.
- Provider checkout, webhook or polling verification, safe checkout closure, refunds, actual processing/platform fees, account eligibility, and settlement require the selected provider account. A simulated report cannot prove those facts.
- Email account/domain sending and delivery evidence require the configured Site-owned email service. HP-OS only queues and records the work.
- Signed Apple Wallet passes, device registration/update pushes, and supported-device behavior require Apple credentials, certificates, and devices held by LMNL. HP-OS can prove unsigned operational Wallet data and durable update work locally.
- Phone-camera scanning and manual door lookup require the intended LMNL device flow. The Admission endpoint and its atomic result remain locally testable.
- Hosted Supabase connectivity, callbacks, Vercel Cron execution, hosted secrets, and a controlled real purchase/refund require hosted or production evidence. Local results do not imply those outcomes.

## Capability and evidence status

As of this research date, the operations and processing below are **unimplemented**, not failing implemented features. Future evidence must distinguish an absent capability from an implemented operation that fails its expected outcome. Also distinguish an implemented check that has not run, a check blocked by missing configuration/service/device/specification, and a passed check with its specific revision and environment. This follows the current [repository status](../../README.md), [implementation specification](https://github.com/fvckzest/HP-OS/issues/22), and [release evidence rules](../release-and-cutover.md#scope-and-release-rule).

The public single-Ticket pricing model from [#28](https://github.com/fvckzest/HP-OS/issues/28) now uses explicit Event tax and buyer-fee inputs plus an Organization-level 10% pilot-fee rate; unknown amounts block checkout. Local API checks cover these configured inputs and their failure states. Provider/account eligibility, enforceable closure, email verification, historical connection access, and Apple/device configuration require their respective integration evidence. Do not treat local configuration as proof of provider settlement.

## Protocol and observable processing coverage

Every applicable route also needs the shared [request, response, and error checks](../api/api.md#detailed-schemas-and-operational-rules): authentication and revoked keys; Site-derived scope and cross-Site related records/tokens/provider references; actor attribution and Site-held staff permissions; required headers; JSON/media-type/body-size validation; unknown fields, enums, safe-integer money, quantity and date validation; structured success/error wrappers and request IDs; correct HTTP status and error code; `Retry-After`; and `no-store` for operational and buyer reads. Lists need filters, deterministic ordering, default/maximum sizes, empty results, and cursor binding/expiry. Key rotation must preserve replay history; replays must retain original results and tokens even after versions or access links change. The direct API and incoming LMNL request boundaries must exercise these same rules.

HP-OS processing must be exercised through the same bounded entry point used by its scheduler, including checkout expiration/verification state, paid issuance recovery, and durable notification work. Assert public/admin Event availability, Order/Reservation/attempt status, complete Ticket sets, jobs, verification frontiers, issues, and totals before and after processing. LMNL processing separately verifies/closes provider attempts, delivers its durable report outbox, claims/rechecks notification jobs, verifies uncertain dispatch, and sends/signs/updates through its services. Run both without visitor requests and restart each independently; an HP-OS worker run alone cannot prove Site work completed ([technology](../technology.md#background-processing), [#25](https://github.com/fvckzest/HP-OS/issues/25), [#34](https://github.com/fvckzest/HP-OS/issues/34), [#45](https://github.com/fvckzest/HP-OS/issues/45)). Every job kind must be covered: `access_approved`, `tickets_ready`, `order_recovery`, `event_changed`, `event_canceled`, and `wallet_update`, including per-recipient/Ticket units, superseded unsent work, and current-data rechecks ([notification rules](../api/api.md#notification-job-schema-and-recovery)).

## Cross-cutting controlled scenarios

Cross-cutting API verification should use a controlled clock and assert the exact boundaries from the contract ([dates and times](https://github.com/fvckzest/HP-OS/blob/8a96e39666a80e82c1d7e16b99976e5e00c522c1/docs/api/api.md#dates-and-times), [lifetimes](https://github.com/fvckzest/HP-OS/blob/8a96e39666a80e82c1d7e16b99976e5e00c522c1/docs/api/api-ref.md#lifetimes-and-limits)):

- Quotes expire at 10 minutes without a hold; Orders stop new payment at 15 minutes. A no-attempt Order can expire, but an uncertain or provider-capable attempt holds capacity until closure/payment is verified.
- Current public Events require `ends_at > now`; at `ends_at` they belong to the past list (`ends_at <= now`). Admission is available from check-in opening through the Event end instant, so the exact end instant is still eligible and the instant after it is closed.
- Use explicit UTC offsets and the named IANA Event time zone. Test default check-in opening after an edited start and an explicit opening that does not move.
- Notification leases last five minutes and are fenced; temporary recovery access lasts 30 minutes; cursors last one hour; idempotent results replay for seven days after completion. Retry delays are 1/2/4/8/16 seconds plus jitter and `Retry-After`.
- Check recovery coalescing at one email/minute and five/hour per Site/email, the default Site-wide 1,200-request/minute budget across keys, notification retry delays of 1 minute/5 minutes/15 minutes/1 hour/6 hours, and durable Site report retries capped at 15-minute intervals after interactive exhaustion. Unknown dispatch remains unresolved until verified; permanent delivery failures require correction or an intentional resend.
- Run concurrent same-key writes, conflicting key reuse, version conflicts, last-capacity Orders, one approval's competing checkouts, one payment-capable attempt, two Admission attempts, two job claims, and overlapping Event/payment/report workers. Assert one durable effect and a replay or conflict response.
- Interrupt after database commit, after a claim, after an external dispatch, and during issuance or Wallet update. Lost responses must be recoverable by the same key or a state read. Unknown external outcomes require verification before resend, and no timeout alone may release capacity, issue a second Ticket, create a second Admission, or send again.

The resulting evidence should record repository revision, environment, scenario, expected result, actual result, and non-secret evidence. A local pass is a local API/LMNL result; it is not hosted readiness, device proof, provider settlement, or permission to open sales. Those evidence boundaries are explicit in the [release procedure](https://github.com/fvckzest/HP-OS/blob/8a96e39666a80e82c1d7e16b99976e5e00c522c1/docs/release-and-cutover.md) and the settled [ownership rules](https://github.com/fvckzest/HP-OS/blob/8a96e39666a80e82c1d7e16b99976e5e00c522c1/docs/ownership.md).
