# Events

## Purpose and ownership

HP-OS owns each Site's operational Event records. LMNL is the first Site and owns staff CRUD and public presentation. Events are not shared between Sites. See [ownership](../ownership.md). The first-release jobs were selected in [ticket #6](https://github.com/fvckzest/HP-OS/issues/6); the journey rules below were settled in [ticket #8](https://github.com/fvckzest/HP-OS/issues/8).

## Setup and publication

- The first release covers new paid public and private Events after all current LMNL Events are complete. Cutover occurs with no active public sales; existing Events and their records remain in the existing system. Historical import is separate future work if needed. See the [release and cutover procedure](../release-and-cutover.md), agreed in [ticket #12](https://github.com/fvckzest/HP-OS/issues/12). Public and private Events both appear in the Site's public event list. A private Event offers an Access Request instead of public checkout. Free ticket issuance is deferred.
- Staff may save incomplete drafts. Publication requires a title, description, start and end dates and times with time zone, venue, and public or private visibility. The end must follow the start and may be days later for a multi-day Event.
- Public or private visibility can change while an Event is a draft but becomes fixed once published. This keeps the access rules stable after visitors see the Event or begin checkout; see [ticket #10](https://github.com/fvckzest/HP-OS/issues/10) and [Event editing rules](../api/api.md#draft-and-published-event-edits).
- Publication and sales are separate. A published Event can be visible before checkout opens. Price, capacity, a scheduled sales opening and closing time, an explicit tax amount, and an explicit buyer-fee list are required before a quote is available. Use zero tax or an empty fee list only when those amounts are confirmed. Unknown values keep sales `not_configured`; [ticket #28](https://github.com/fvckzest/HP-OS/issues/28) fails closed rather than guessing.
- The Organization's 10% pilot platform fee is an explicit setup value, not a global default. The operator can set it when creating an Organization or configure it afterward. An Organization without that value cannot produce a quote.
- After price, capacity, both sales times, tax, and buyer fees have been saved, later edits cannot clear those configured values to `null`; staff can still replace them with valid values. This keeps an established Ticket offering from unexpectedly returning to an unconfigured state, as agreed in [ticket #26](https://github.com/fvckzest/HP-OS/issues/26) and extended for checkout pricing by [ticket #28](https://github.com/fvckzest/HP-OS/issues/28).
- HP-OS reports the authoritative sales status using the order in the [API contract](../api/api.md#public-and-admin-event-responses). `stop_sales` and `resume_sales` are versioned, idempotent actions. Resume succeeds only for a paused, eligible Event whose complete sales window is currently open and whose offering has capacity remaining. These controls are implemented locally under [ticket #27](https://github.com/fvckzest/HP-OS/issues/27). Stop/resume actions do not create or release Reservations; availability and capacity guards use the Reservation-backed committed quantity managed by the checkout flow introduced under [ticket #28](https://github.com/fvckzest/HP-OS/issues/28).
- Effective check-in opening defaults to the Event start time unless staff saved an earlier explicit value. The API returns the effective value and indicates whether it uses the default; this is display data and does not implement Admission scanning.
- An Event becomes past automatically at its end time. Staff may archive an ended or canceled Event; archiving removes it from the current-event list but preserves its details, direct page, Orders, Tickets, and history. A Site may still show archived Events in a past-events view. Archiving does not change payment or admission status.

Separate publication and sales controls let Sites announce Events early without exposing an incomplete checkout. Preserving archived data keeps past Events and buyer records available.

## Sales and capacity

- Staff may stop new checkouts immediately and resume them while the Event is not canceled, its scheduled sales window is open, and capacity remains. A manual stop lets active checkouts finish.
- Checkout reserves the requested Ticket offering quantity without exceeding available capacity. The buyer has 15 minutes to start payment. At expiration, capacity releases only when no provider checkout can still take payment. The Site verifies and closes any existing checkout before release; processing or uncertain results keep their Reservation until verified. See [checkout expiry](../api/api.md#checkout-expiry-and-provider-verification).
- When an unpaid Reservation releases capacity, a sold-out Event becomes available automatically if the sales window is open and staff have not stopped sales.
- Capacity cannot be reduced below Tickets already admitted, issued Tickets still valid for Admission, and active Reservations. The local API now records and releases single-Ticket prepayment Reservations through the bounded processor; issued Ticket and Admission accounting remains future work. A fully refunded Ticket returns to sale capacity only if it was never admitted.
- A price edit affects only checkouts started afterward. Paid Orders and active checkouts retain their original quoted price.

These rules prevent overselling, release abandoned capacity, and keep purchase terms stable while staff make corrections.

## Event changes and cancellation

- After sales begin, staff may change the start or end date and time, time zone, or venue. HP-OS validates the complete Event timing and sales window, then creates one durable `event_changed` job per paid Order in the same transaction as the edit. If job creation fails partway through, the Event edit and inserted jobs all roll back. A later arrival change supersedes only earlier jobs that have never been attempted or claimed. See the exact payload in the [API contract](../api/api.md#notification-job-schema-and-recovery), settled in [issue #40](https://github.com/fvckzest/HP-OS/issues/40).
- Order and individual Ticket pages show current Event details from HP-OS, so a later visit reflects an accepted time or venue change. The Site worker sends each durable change job using Site-owned credentials; HP-OS does not send email.
- Each Event has a check-in opening time, defaulting to its current start time. Rescheduling updates that default automatically; an explicit saved opening remains at its saved time. Admission is available through the Event's end time. Scans outside that window create no Admission.
- Cancellation is a version-guarded action for a current, published Event. It immediately blocks new Orders and Ticket Admission, ends unpaid checkout permission, and releases only Reservations that have no unresolved provider-capable attempt. Reservations with possible provider payment remain held and visible for Site verification. HP-OS keeps the Event and purchase history, queues `event_canceled` work in the same transaction, and shows cancellation separately from refund status on the Order page. This behavior is implemented for [issue #41](https://github.com/fvckzest/HP-OS/issues/41).
- Cancellation does not initiate a refund. Staff refund through the payment provider's dashboard; HP-OS reflects the provider-confirmed status separately. A charge confirmed after cancellation is recorded as paid, Ticket issuance is blocked, held capacity is released after the payment is known, and an actionable staff issue is created.

### Event fan-out size and mutation budget

Issue [#127](https://github.com/fvckzest/HP-OS/issues/127) defines the first Event fan-out engineering target at **1,000 paid Orders and 8,000 issued Tickets for one Event**. Arrival edits, cancellation, and archival must complete their HP-OS transaction, including required notification and Wallet outbox work, within a **5-second local PostgreSQL mutation budget** at that size.

The runtime configuration does not yet provide a hosted duration to bind this target to: `package.json` requires Node.js `>=22.6`, the `/v1/[...path]` route is dynamic but does not declare a separate runtime or `maxDuration`, and `vercel.json` defines only the Cron schedule. Until the deployment supplies and records its function runtime and duration limit, the 5-second value is a local engineering budget measured against the repository's Node.js and PostgreSQL setup. It is not hosted runtime evidence or a hosted performance claim.

The large fan-out path keeps recipient rows in PostgreSQL: Event notifications use one `INSERT ... SELECT` over paid Orders, and Wallet jobs use one `INSERT ... SELECT` over issued Tickets with the post-mutation data-version digest calculated in the database. This keeps application memory and database round trips bounded by the mutation shape rather than by the number of recipients, while the inserts remain in the caller's transaction. The repeatable synthetic scenario is `pnpm benchmark:events`; it records mutation duration, the harness-held Event lock interval, checkout and claim overlap, rollback, retry, job counts, and Site isolation. The lock interval is an intentional test hold and is not a direct PostgreSQL lock-wait measurement. It does not call a provider, email service, Apple device, hosted deployment, or cutover system.

The public Wallet contract returns one Ticket per request and applies the Site request budget, whose default is 1,200 requests per minute. For its synthetic fixture only, `pnpm benchmark:events` raises that limit to 10,000 requests per minute and checks all 8,000 arrival Wallet responses with bounded concurrency; this keeps the parity sweep within one local window without changing the product default. The latest local run on 2026-10-08 checked all 8,000 arrival responses in 21,630 ms and matched each response to its queued arrival `data_version`. Arrival completed in 791 ms, the intentional Event lock hold was 104 ms, the overlapping Event mutation completed in 208 ms, the quote returned HTTP 201 in 159 ms, the claim returned HTTP 200 in 158 ms, cancellation completed in 701 ms, and archival completed in 681 ms. Separately, the run produced 1,000 `event_changed` jobs, 1,000 `event_canceled` jobs, and 24,000 Wallet jobs; cardinality checks found exactly one Wallet job per Ticket after arrival and exactly three after the three fan-outs. These are local synthetic measurements only and are not hosted-runtime evidence.

Reproduction record for those measurements: benchmark code revision `75b785e31f9e0f60c788a6358bf93c868f99616e`, Darwin 27.2.0 arm64, Node.js v24.18.0, Next.js 16.3.6 using the webpack development server, and PostgreSQL 17.6 on `aarch64-unknown-linux-gnu`. The local boundary was HTTP `127.0.0.1:3306` to the HP-OS app and database `127.0.0.1:54322`; the run used only this local HTTP and database path, seeded synthetic data, and removed the fixture afterward. Expected results were 1,000 paid Orders, 8,000 issued Tickets, all covered Wallet responses matching their queued digest, and each covered mutation within 5,000 ms; the actual results above met those expectations. No credentials or external-service calls were used, and this environment record does not establish a hosted runtime or hosted `maxDuration`.

Notifying buyers of changed arrival details and cancellation keeps the public journey accurate. Keeping refund status separate avoids implying money was returned before the provider confirms it.

HP-OS durably queues the required notifications; the Site backend sends them using its own credentials and reports outcomes. This keeps credentials outside HP-OS while preserving notification recovery and visibility, as decided in [ticket #10](https://github.com/fvckzest/HP-OS/issues/10). Cancellation notices do not claim that an Order has been refunded; they direct buyers to the separate refund status. See [notification jobs](../api/api.md#notification-jobs).

## Presentation and API boundaries

Featured and home-page selection remain LMNL controls. Manual event-page and checkout-link overrides, arbitrary custom traits, and the Square test-item action are outside normal first-release Event setup. See [ticket #6](https://github.com/fvckzest/HP-OS/issues/6).

For [issues #26](https://github.com/fvckzest/HP-OS/issues/26) and [#27](https://github.com/fvckzest/HP-OS/issues/27), LMNL saves new Event drafts, publishes them, displays HP-OS's purchase mode and sales status, and provides staff stop/resume controls through its server-side proxy. [Issue #28](https://github.com/fvckzest/HP-OS/issues/28) adds single-Ticket quotes and unpaid Orders through the same server-side boundary. [Issue #29](https://github.com/fvckzest/HP-OS/issues/29) adds a buyer total and identity step followed by a Square-hosted link for public HP-OS Events. [Issue #30](https://github.com/fvckzest/HP-OS/issues/30) adds local Site-verified payment reporting, retryable Ticket issuance, and buyer reads. HP-OS owns the Site-scoped Event, Organization fee configuration, accepted quote, Order, frozen payment connection, payment attempt, Reservation, and Ticket; LMNL remains responsible for provider credentials, Square calls, staff authentication, and public presentation. Existing LMNL Event records stay on their current integration, and new Events do not change featured or home-page selection. LMNL public lists request current and past HP-OS Events, while direct pages use the existing `/events/:slug` presentation route. The Issue #30 LMNL integration remains Draft through cutover, and its local checks use synthetic provider evidence; hosted deployment, live payment confirmation, cutover, and fee settlement remain unverified. LMNL checkout remains in Draft [PR #85](https://github.com/fvckzest/LMNL/pull/85) until cutover.

An Event belongs to one Site and has one priced Ticket offering in the first release. The offering is the sale option and capacity, not an issued Ticket. See the [domain glossary](../../CONTEXT.md). The Site API must keep archived Event details retrievable for past-event presentation; exact operations and payloads belong to [ticket #10](https://github.com/fvckzest/HP-OS/issues/10) and [docs/api/api.md](../api/api.md).

The Ticket offering may optionally be associated with an existing payment-provider resource on a payment connection. HP-OS remains authoritative for price and capacity, and this association does not enable per-Event provider selection. Optional association supports checkout without requiring a preexisting catalog resource. Automatic provider catalog creation is deferred beyond the first release to avoid adding a catalog synchronization workflow. See the [decision in ticket #10](https://github.com/fvckzest/HP-OS/issues/10) and [offering provider mapping](../api/api.md#offering-provider-mapping) for the API boundary.
