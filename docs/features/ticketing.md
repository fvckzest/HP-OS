# Ticketing

Issue #43 implements Site-scoped Order and Ticket lists, one-snapshot Event totals, and actual processing/platform fee reporting. Fee components retain provider source revisions and conflicts; explicit confirmations are required before aggregate fee values become complete, so missing information stays pending. Completeness follows provider observation time, so a late-submitted stale confirmation cannot close a newer fee revision. LMNL presentation and provider settlement remain cutover proof.

## Purpose and ownership

HP-OS owns each Site's Buyers, Orders, Reservations, Tickets, Admissions, and sales totals. LMNL is the first Site. The first-release jobs were selected in [ticket #6](https://github.com/fvckzest/HP-OS/issues/6); the journey rules below were settled in [ticket #8](https://github.com/fvckzest/HP-OS/issues/8). See [ownership](../ownership.md) and the [domain glossary](../../CONTEXT.md).

## Private Access Requests

Issues [#46](https://github.com/fvckzest/HP-OS/issues/46) and [#47](https://github.com/fvckzest/HP-OS/issues/47) implement the HP-OS private Access Request and one-purchase capability. Public Tickets continue to return `approved_attendee: null`; private Tickets retain the approved attendee snapshot on the Order and Ticket. Local API verification covers the HP-OS boundary. LMNL presentation, approval email delivery, provider checkout, and other external integration checks remain deferred under the [release and cutover policy](../release-and-cutover.md#repository-wide-deferral-and-issue-closure).

- A private Event appears publicly with an Access Request form. An approved request permits one paid Ticket; it is permission to begin checkout, not an Order or Reservation.
- Each Access Request requires the intended attendee's name and email so admin users can vet whose admission they are approving, even when another person will pay. Checkout separately collects the purchaser's details, and the Ticket retains its association with the approved attendee. Public checkout continues without individual attendee details. See [ticket #10](https://github.com/fvckzest/HP-OS/issues/10) and [Access Request operations](../api/api.md#access-request-operations).
- The Site passes the approval token when requesting the one-Ticket private quote and again when creating the Order. HP-OS checks that the token belongs to the same Site, Event, and approved request on both calls. The purchaser's name and email become the Order's checkout identity; they do not replace the approved attendee.
- Multiple independent requests for one Event may use identical attendee names and emails. Each requires its own approval and permits one paid Ticket; private multi-ticket Orders remain deferred. This keeps repeated requests simple while maintaining approval per request. See [ticket #10](https://github.com/fvckzest/HP-OS/issues/10).
- Approval queues an `access_approved` notification containing the approved attendee and approval token; the Site backend sends the checkout link when its email integration is active. Approval does not hold capacity. The link works until sales close, permits payment retries, and can produce only one successful purchase. If capacity runs out first, it shows a sold-out outcome.
- Rejection queues no email. Staff may undo either decision and reconsider the request. Undoing approval before payment disables its token and ends an unpaid checkout; approving again creates a new token and notification job. After payment, undoing the request decision does not change the paid Order or Ticket.
- Correcting attendee details on an approved, unpaid request exceptionally requires undoing approval and approving the corrected request again. Normal checkout carries the approved attendee details forward without collecting them again; purchaser-detail changes do not alter the approved attendee. This preserves the vetted identity without adding a routine correction step; see [ticket #10](https://github.com/fvckzest/HP-OS/issues/10).

This keeps the private approval queue separate from public purchases and prevents unused approvals from consuming capacity. HP-OS does not store Site email credentials or send mail itself; a local job and token check therefore do not prove mailbox delivery.

## Public checkout and payment

- Public checkout supports one to eight Tickets per Order, while approved private checkout remains one Ticket. The Site collects the Buyer's real name and email. Before a buyer proceeds, it shows the complete HP-OS quote in the correct currency. Quote requests with no remaining capacity return `sold_out`; requests with some capacity remaining but less than the requested quantity return `insufficient_capacity`, and neither response creates a hold. Because quotes do not reserve capacity, Order creation checks the full quantity again. Event setup records an explicit tax amount per Ticket and a buyer-fee list; the quote scales those per-Ticket values by quantity, and zero tax and an empty fee list mean staff confirmed those amounts do not apply. Missing inputs keep sales unconfigured and block checkout. The one-Ticket pricing inputs were implemented in [ticket #28](https://github.com/fvckzest/HP-OS/issues/28); public group checkout and its private one-Ticket boundary were implemented in [ticket #50](https://github.com/fvckzest/HP-OS/issues/50).
- The platform fee is separate from the buyer total. An operator explicitly configures the Organization's 10% pilot rate; HP-OS includes the expected fee in the quote so the Site can pass it to its provider. For public group checkout, HP-OS calculates it from the aggregate pre-tax Ticket subtotal and rounds to the nearest minor currency unit. This Organization-level setup follows [ticket #28](https://github.com/fvckzest/HP-OS/issues/28), and quantity handling follows [ticket #50](https://github.com/fvckzest/HP-OS/issues/50). Actual provider fee settlement remains unverified.
- New Orders freeze the currently assigned, operator-verified payment connection. The Site verifies the configured provider, environment, seller, location, currency, and required Square access before creating the hosted checkout. Draft LMNL PR #85 implements a Square Payment Link with a catalogless quick-pay line item, priced at the exact HP-OS Order total; the PR remains Draft until cutover. It does not create or update Square catalog items. Square Sandbox cannot collect `app_fee_money`; Sandbox testing may record the platform fee as ineligible and leaves it out of the provider request. A live connection must have recorded platform-fee eligibility before it can open checkout. These Site-owned checks and the frozen Order connection were implemented for [ticket #29](https://github.com/fvckzest/HP-OS/issues/29).
- HP-OS creates one payment attempt before the Site calls Square. Draft LMNL PR #85 registers the returned payment-link reference with HP-OS before redirecting the buyer. An unresolved attempt blocks a second payment-capable checkout for the same Order. If Square setup fails before creating a link, the Site can report a confirmed not-started outcome. If a link may exist or a response is uncertain, the Reservation remains held. The LMNL implementation in Draft PR #85 closes a registered link and reports closure only after Square reports its associated Order as canceled; uncertainty keeps the hold. See [checkout expiry](../api/api.md#checkout-expiry-and-provider-verification).
- The buyer has 15 minutes to start payment. An Order without a payment attempt can expire directly. After verified closure inside the deadline, HP-OS permits a replacement attempt while keeping the same Reservation; after the deadline, it releases capacity only when provider checkout is confirmed closed and no payment result is unresolved. This protects capacity from an unpaid but still payable Square link. The bounded scheduler marks at most 50 overdue unresolved attempts per transaction for Site verification in deterministic order, and the Site worker discovers that frontier after restart through `GET /v1/admin/payment-attempts?requires_verification=true`; the Site verifies the recorded provider checkout before reporting closure. Local checks cover synthetic HTTP and database behavior; actual provider closure and delayed confirmation remain cutover evidence.
- Returning from Square does not confirm payment or issue Tickets. Issue #30 implements Site-verified payment outcome reporting, a durable LMNL report outbox, and a short-lived opaque return reference that exposes only current payment and issuance status. The LMNL webhook verifies Square's signature and retrieves current Square payment and Order records before reporting through the Site API. HP-OS commits a valid paid report before issuing the complete Ticket set and queuing the initial email; a failure leaves payment recorded and issuance retryable. Issue #35 retains conflicting observations, marks the payment attempt for verification, exposes the report and investigation issue to Site staff, and permits only a version-guarded resolution with a new verified source reference and matching payment facts. Issue #36 records a durable `ticket_issuance_failed` issue when confirmed payment cannot finish the complete set and resolves that issue only when issuance and the initial `tickets_ready` job commit together. The bounded scheduler retries paid pending/failed Orders without visitor traffic; `POST /v1/admin/orders/{order_id}/actions/retry_ticket_issuance` requires the current Order version and refuses canceled Events, full refunds, released Reservations, missing buyer access, existing Tickets, or other non-awaiting states. A valid paid resolution commits payment before the normal retryable issuance step; an unresolved conflict never appears paid. Site workers can discover later unapplied stale reports through `GET /v1/admin/payment-attempts?requires_report_work=true`; resolved conflict history is not requeued, and the filter never changes payment state. Local PostgreSQL verification deliberately interrupts database Ticket issuance and exercises automatic recovery, guarded recovery, buyer access, and durable staff evidence through normal HTTP boundaries. Whole-second Event timestamps retain their RFC 3339 `Z` or offset in the `tickets_ready` payload, so notification validation accepts those recovery cases. Hosted worker interruption, live Square webhooks and provider confirmation, hosted checkout, email delivery, and cutover behavior remain deferred evidence. LMNL's Issue #30 and #36 integrations remain Draft until the later cutover. The provider return URL is presentation only. This preserves the [payment execution boundary](../ownership.md#data-separation-and-payment-execution) settled in [ticket #9](https://github.com/fvckzest/HP-OS/issues/9).
- A confirmed payment with failed Ticket issuance leaves the Order paid and awaiting Tickets. HP-OS issues a multi-ticket Order's complete set together, retries safely without duplicates, and alerts staff if recovery remains unresolved. Staff can use a guarded retry action. The complete set is atomic: a failed issuance attempt does not expose a partial Ticket set.

These rules prevent overselling and presenting an unpaid or incomplete Order as a successful purchase.

## Delivery, Order access, and buyer correction

- The initial ticket email is the normal access path. It contains one hard-to-guess link that opens the Order page directly without login or an emailed code. That page contains all Tickets; each Ticket has its own QR and admission-status page and can be shared separately. Anyone given the Order link can access every Ticket in it.
- A group can show all Tickets from one Order page; door staff scan each QR in turn. A buyer who loses the email can request a time-limited Order link sent only to the current delivery email. LMNL verifies a Turnstile challenge before forwarding the request. HP-OS returns the same acknowledgment when no Order matches or a send is suppressed, and coalesces requests to at most one recovery email per normalized Site/email each minute and five each hour. The temporary link lasts 30 minutes and supports repeated reads for page refreshes; it does not return the permanent Order token. Delivery-email correction revokes outstanding temporary links. Entering an email address alone never reveals whether an Order exists. This flow was implemented for [ticket #38](https://github.com/fvckzest/HP-OS/issues/38); see [lost-email Order recovery](../api/api.md#lost-email-order-recovery).
- Ticket issuance and validity do not depend on email delivery. HP-OS durably queues and tracks required notification work, including retry work for failed dispatch or delivery; the Site backend sends emails using its own credentials and reports outcomes. Failed dispatch reports carry an explicit `transient` or `permanent` classification, and omitted classifications default to `transient`; HP-OS does not infer retryability from provider message text. Staff can request a resend only after the newest applicable Ticket-email job has a confirmed failure. Pending, sent-without-delivery, delivered, and unknown outcomes remain guarded; an unknown outcome requires provider or durable Site-log verification before another send. Superseded jobs are excluded from current state and claims. The Order page remains available after issuance. This execution boundary was settled in [ticket #10](https://github.com/fvckzest/HP-OS/issues/10) and the recovery behavior was implemented for [ticket #37](https://github.com/fvckzest/HP-OS/issues/37); see [notification jobs](../api/api.md#notification-jobs).
- After verifying the purchase, authorized staff can correct a mistyped delivery email when the newest applicable Ticket-email job has a confirmed dispatch or delivery outcome. HP-OS rejects pending, sent without a delivery report, unknown, missing, and superseded current jobs with stable `409` state fences; confirmed failed and delivered outcomes support correction. It waits for an actively pending latest delivery job to settle before applying the correction, so a claimed Ticket-email worker cannot send superseded links. It associates the Order with the Site Buyer for the corrected address without rewriting an existing Buyer's profile name, invalidates old Order and individual Ticket page links, revokes temporary recovery links, and removes the corrected Order from pending recovery jobs that have no active claim or unresolved provider outcome, including transient retry work. It then issues replacement page tokens and queues delivery to the corrected address. A recovery email job already claimed before correction remains in the worker's reconciliation flow; LMNL must reread each temporary Order link through HP-OS immediately before sending, omit revoked, expired, or no-longer-current-address links, and skip a job with no valid links. Previously shared Ticket links must be shared again. The immutable `checkout_identity`, Ticket IDs, QR payloads, Wallet identity, and Admission history stay unchanged. Future Order lookup uses only the corrected email. Delivery jobs and the guarded correction audit record remain visible. This worker race rule is implemented for [ticket #39](https://github.com/fvckzest/HP-OS/issues/39); Wallet-device behavior and LMNL private-approval integration remain later proof.
- Delivery-email correction preserves admission QR codes and existing Wallet passes. Previously captured screenshots and saved passes still work while the Ticket is eligible; one successful Admission per Ticket remains enforced. Wallet passes are not voided solely for email correction and still reflect cancellation, full refunds, and used status. Normal resends and recovery also preserve QR codes. This keeps existing QR presentations usable, as decided in [ticket #10](https://github.com/fvckzest/HP-OS/issues/10).
- Repeat Orders with the same purchase email on a Site associate with one Buyer. Each Order keeps its own checkout name and email; Sites never share Buyer records.

Separating access links, delivery state, and historical checkout details supports buyer recovery without rewriting purchase history.

## Admission and Wallet

- The Site backend authorizes a limited door role for the selected Event before using HP-OS; door staff do not receive full Event administration permission. HP-OS authenticates the Site API key and enforces Site/Event scope and current Ticket eligibility.
- A phone camera sends the stable QR admission token to the Site backend unchanged. If scanning fails, staff can search the Event by exact Order reference or current delivery email, review matching Tickets, select one, and explicitly confirm Admission. Lookup never admits a Ticket and does not expose buyer page-access tokens.
- Admission rechecks eligibility when called and records at most one successful Admission per Ticket, including at multi-day Events. Invalid, wrong-Event, already-admitted, early, late, canceled, and fully refunded Tickets do not create Admissions. These door-access and check-in rules were implemented for [ticket #32](https://github.com/fvckzest/HP-OS/issues/32); see the [API contract](../api/api.md#admission-operations) for request and response details.
- If the device loses HP-OS connectivity, it shows unable to verify and records no offline Admission. If a request may have succeeded but its response is uncertain, the Site retries the same request with the same idempotency key to retrieve the original result; a new scan is a separate attempt.
- Admission is allowed from the Event's check-in opening time through its end time. Simultaneous attempts against one Ticket must produce exactly one successful Admission.
- Each Ticket can be added to Apple Wallet. HP-OS supplies the current unsigned Wallet data through the Site-scoped buyer-token and admin-Ticket reads implemented for [ticket #48](https://github.com/fvckzest/HP-OS/issues/48). An updatable pass receives current Event time and venue, shows used status after Admission, and becomes void after cancellation or a full refund. [Apple supports pass updates](https://developer.apple.com/documentation/walletpasses/adding-a-web-service-to-update-passes) and a [voided field](https://developer.apple.com/documentation/walletpasses/pass). Device updates may arrive later, so the live HP-OS admission result remains authoritative.
- The Site backend generates and signs Wallet passes and holds the signing credentials. HP-OS retains no Site or organization service credentials and supplies authoritative operational data instead. This keeps credential custody on the Site; see [ticket #10](https://github.com/fvckzest/HP-OS/issues/10) and [external service credentials](../ownership.md#external-service-credentials).
- HP-OS durably queues required Wallet update work for the Site backend to execute and report, alongside email notifications. See [ticket #10](https://github.com/fvckzest/HP-OS/issues/10) and [notification jobs](../api/api.md#notification-jobs).
- HP-OS queues one `wallet_update` job per affected issued Ticket in the same transaction after a published Event edit that changes stable pass-visible content, arrival/check-in details, or price, Event cancellation or archival, successful Admission, or a full refund. A full refund queues every issued Ticket, including already admitted Tickets, while capacity restoration remains limited to unadmitted Tickets. Clock-derived sales availability, email correction, and partial refunds do not queue Wallet work; live HP-OS Admission remains authoritative. This transaction boundary was implemented for [ticket #49](https://github.com/fvckzest/HP-OS/issues/49).
- Wallet templates, artwork, logos, images, layout, and presentation text belong to the Site. The Site combines them with current HP-OS Event and Ticket data and regenerates passes when either operational data or its own presentation changes. This keeps presentation Site-owned; see [ticket #10](https://github.com/fvckzest/HP-OS/issues/10) and [Wallet generation](../api/api.md#apple-wallet-generation).

## Refunds and event totals

- Staff perform refunds in the provider dashboard; the Site backend verifies each provider refund against the original payment and durably reports it to HP-OS. HP-OS deduplicates provider refund identities across current and historical connections, serializes source references across Events within a Site, keeps stale and conflicting observations, and opens a staff issue when amounts or references conflict. A refund received before payment confirmation returns a retryable `503 payment_not_confirmed` without retaining a source or Idempotency-Key result. Cumulative completed refunds cannot exceed the confirmed payment amount. This lifecycle was implemented for [ticket #42](https://github.com/fvckzest/HP-OS/issues/42); actual Square/provider confirmation remains cutover evidence.
- A full Order refund makes its Tickets unusable for future Admission while retaining Order, Ticket, and prior Admission history. HP-OS returns sale capacity once for each unadmitted Ticket; an admitted Ticket keeps its Admission and does not return capacity. A full refund before issuance releases the held Reservation and prevents a later Ticket issuance. Refund processing serializes with Admission. A partial refund changes money status but does not automatically revoke Tickets.
- Event cancellation in [issue #41](https://github.com/fvckzest/HP-OS/issues/41) does not itself refund. A charge confirmed after cancellation remains recorded as paid, opens an actionable staff issue requiring refund review, and creates no usable Tickets. Buyer cancellation notices and Order pages keep Event cancellation, late payment, and refund status separate.
- The Site API exposes gross paid sales, refunded amount, and net sales; net is gross less refunds. It also exposes Tickets issued, valid, and admitted as separate counts. Valid counts exclude canceled and fully refunded Tickets, but do not depend on the check-in clock and can overlap admitted counts; immediate entry eligibility is reported separately as `can_admit`. An issued but fully refunded Ticket remains in issued history but no longer counts as valid.
- Event totals also report provider processing fees and LMNL platform fees separately so admin users can see each deduction. Fees use actual provider-confirmed amounts reported by the Site backend; missing fee information is explicitly pending and cannot appear as zero or as a confirmed estimate. Fee amounts and fee-only currencies are drawn from currently paid or completed-refund scopes without retained fee conflicts for the category. A retained conflict removes that scope/category's fee amounts and confirmation-only currencies while keeping that category pending; processing and platform reporting remain independent. The platform fee expected at checkout is separate from confirmation of what LMNL received. Net sales retains its definition above. This reporting scope and confirmation boundary were settled in [ticket #10](https://github.com/fvckzest/HP-OS/issues/10); exact fee fields and confirmation behavior are defined in the [API contract](../api/api.md#event-totals-response).
- Each fee category shows charged amounts, confirmed returns or credits, and net fees separately. Net fees are charged amounts less returns. A buyer refund does not imply a fee return without separate provider confirmation. This preserves fee history and shows the retained amount; see [ticket #10](https://github.com/fvckzest/HP-OS/issues/10).
- Staff can inspect Event ticket holders, each Order's payment and issuance status, and these basic totals. Provider settlement information remains the accounting source.

These separate totals show both historical sales and current entry rights without implying a separate reconciliation report.

## Release proof

Repository-wide, LMNL implementation/integration and all hosted, provider, email, Wallet/device, and cutover proof are deferred until the user explicitly declares the cutover window. These release checks do not block closure of a completed HP-OS implementation issue. [Ticket #12](https://github.com/fvckzest/HP-OS/issues/12) defines the later [LMNL release checklist and cutover procedure](../release-and-cutover.md). Once activated, local and hosted tests precede a controlled real purchase and refund. Every required check must pass, and the user must explicitly approve opening sales. Cutover happens after all current Events are complete, with no active public sales; historical records remain in the existing system.

Before the first release, prove a complete single-ticket purchase, then a multi-ticket purchase, using provider-confirmed payment, the initial ticket email, Order page, separate QR pages, one successful Admission per Ticket, and an already-admitted repeat scan. Also prove private Access Request approval, email, one-ticket purchase, and prevention of a second successful use of the approval link.

Local PostgreSQL verification deliberately exercises delayed payment confirmation, Ticket issuance failure, automatic recovery, guarded recovery, and staff visibility for unresolved work through the normal HTTP boundaries. Before release, repeat those scenarios end to end with hosted workers, provider webhooks and confirmation, ticket email delivery, and the controlled cutover. Two door devices must attempt the same Ticket nearly simultaneously and produce exactly one Admission. Cancel a sold Event, confirm buyer notification and blocked Admission, then process a provider refund and verify Order status and Site API totals. These are end-to-end checks; isolated quantity support or unit tests do not prove the journey. See [ticket #8](https://github.com/fvckzest/HP-OS/issues/8).
